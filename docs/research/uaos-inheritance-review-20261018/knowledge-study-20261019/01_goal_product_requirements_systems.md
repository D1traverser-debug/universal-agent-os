# 01｜目标、产品发现、需求工程与系统思维：专题知识库

状态：SOURCE_STUDY__APPLICATION_CANDIDATE；日期：2026-10-19；来源所属：既有 `uaos:maintenance:inheritance-review-20261018` / `EVO-20261018-INHERITANCE-REVIEW`。这是研究证据与方法候选，不是新的需求权威、产品路线图或已部署执行逻辑。

## 1. 研究问题和范围

用户反复追问“知道所有需求吗、产品经理思维吗、有大纲和系统思维吗、为什么要这样要求”，真正要求总控能够在用户未枚举全部要求、方案尚不确定时，主动发现系统目的、实际利益相关方和副作用。研究对象包括需求工程、产品发现、系统工程、架构权衡及反馈。不要把用户提出的措施（如“所有维度每轮深研”）直接等同于最终产品目标，亦不能忽略其作为明确运行约束的地位。

## 2. 一手方法逐项学习

### P01 — NASA System Design Processes
来源：https://www.nasa.gov/reference/4-0-system-design-processes/
- 原方法：Stakeholder Expectations → Technical Requirements → Logical Decomposition → Design Solution Definition，四个过程**相互依赖、反复递归**；一致后继续以真实期望检验设计；尤其不能只依靠最初收到的要求直接设计。
- 本质：系统目标、工作概念（ConOps）、推导需求和架构必须彼此校正，不存在先写完需求再机械实现的单向通道。
- UAOS 吸收：先锁定当前总目标、各子域价值、用户与宿主权威边界；针对每个候选机制回查“为什么需要、给谁带来价值、怎样实测、会破坏什么”。
- 不适用：不能将 NASA 航天项目的重型文档和评审次数原封不动放到每个聊天回合。
- 反证：如果六维研究完成但一次准确的简单交付失败，系统工程的目标验证没有通过。

### P02 — ISO/IEC/IEEE 29148:2018 Requirements Engineering
来源：https://www.iso.org/standard/72089.html
- 原方法：系统/软件生命周期需求过程、需求内容和信息项的规范；ISO 页面确认 2018 版仍有效、正在修订。完整版需付费，本库只采用官方公开简介，不臆测标准的受限全文。
- 学到：需求需要权威来源、明确语义、验证方法、变更影响和追踪，而不是记录为漫长提示。
- UAOS 适配字段：`requirement_id / original_statement / interpreted_outcome / acceptance / owner / constraints / evidence / derived_from / conflicts / revision / unresolved`。作为**建议的语义结构**，不新建第二个状态所有者。
- 竞争意见：过度细分每条需求会制造噪声；仅重要、易变、会跨层传播的需求需要完整持久追踪。

### P03 — INCOSE Systems Engineering Handbook
来源：https://www.incose.org/resources-publications/technical-publications/se-handbook/
- 原方法：把系统看成跨生命周期的相互作用对象，并协调架构、验证、运行、变更与接口。
- UAOS 适配：总控的对象至少包括当前对话宿主、GitHub 授权工具、父治理所有者、四个业务所有者、用户授权、真实产品交付。
- 失效样本：仓库 Python 的受控门禁通过，但真实 ChatGPT 根本没调用；这种组件局部正确、系统整体失效正是需要跨边界审视的问题。

### P04 — Teresa Torres, Opportunity Solution Tree / Continuous Discovery
来源：https://www.producttalk.org/discovering-solutions/
- 研究机理：Outcome → Opportunities（真实需求、痛点、愿望）→ 多个 Solutions → Assumption tests；生成式访谈发现机会、评价性假设测试选择解法，两者不可相互取代。
- UAOS 适配：在修复之前列出至少“不改现状、修改现有实现、替代路线/外部能力、移除不必要机制”的可行候选；选择依据为当前目标证据，不是代码行数。
- 反证：用户提议“全维度深研”，不能只比较是否能在 CI 里填满六个格子；需要探索真正机会是否为“降低漏判、减少用户提醒、提升目标完成度”。

### P05 — SEI ATAM Architecture Tradeoff Analysis
来源：https://www.sei.cmu.edu/library/the-architecture-tradeoff-analysis-method/
- 核心：按具体质量属性场景评价架构，检验性能、安全、可修改性、可用性等属性的冲突和权衡。
- UAOS 对照：增加强制全维度研究可增加形式覆盖，但损失响应效率、可靠性和真实目标贴合；即使用户明确要求每轮深研，仍需评估延迟、成本和答案精度，不得擅自简化用户约束。
- 测试：比较旧策略、强制逐格、目标驱动关系展开三种执行方案；记录被遗漏的专业因素与误判率，不能只数引用。

### P06 — Model-based requirements linked to architecture
来源：https://arxiv.org/abs/2410.21288
- 论文在 NASA JPL 场景检验需求语句与 SysML 架构模型关联可追溯性，提醒需求和结构分离会造成重复或语义漂移。
- UAOS 迁移：追踪“用户目标 → 能力 → 实际执行接口 → 行为证据 → 最终业务验收”，要能够定位哪个关联失效。
- 限制：论文实验不等于对 UAOS 图数据库方案的证明；不因此新增复杂 SysML 仓库或图引擎。

## 3. 总体需求图：开放世界，不是15项封闭分类

最上层 outcome：**减少用户承担的发现、判断、催促成本，让受授权的 Agent 在真实业务中持续取得正确、可验证的成果，并从经验中增强能力。**

需求图具有六种不同节点：
- GOAL：用户最终价值与成功条件；
- REQUIREMENT：用户明确要求、派生约束、待确认隐含需求；
- CAPABILITY：如何感知、研究、规划、执行、恢复、评估、学习；
- CONTEXT/OWNER：宿主、权限、任务、业务所有者、依赖；
- EVIDENCE/OUTCOME：观测事实、验证者、时间、产品验收；
- ALTERNATIVE/DECISION：方案和不采用的解释。

边可为 `derives-from`、`serves`、`conflicts-with`、`depends-on`、`implemented-by`、`verified-by`、`invalidates`。此结构是建模语义，不要求立刻新建图数据库。

原15项工作关注点应作为检索提示、实例化角色和风险提醒，而不是以“一条信息必须落到一类”方式分箱；任何任务允许同时映射多个节点，遇到新对象或关系新增类型而非强制假装已有。

## 4. 真实 UAOS 需求归纳与尚未证实项

- R01 自主发现：没有用户指出问题时也能主动发现未知缺陷或机会。状态：目标已知；独立真实行为证据不足。
- R02 完整研究：用户明确要求每轮所有维度都做实质深研。状态：要求已确认；受控结构门禁不等于语义深度。
- R03 跨学科综合：根据任务调用产品、架构、软件、管理、知识、交互、工具和专业业务方法。状态：候选来源可研究；综合结果未验收。
- R04 独立批判：用户、Agent、自身过去 PR 和网上方案都只作为待验假设。状态：当前 PR #163 缺乏这种语义证明。
- R05 多路求解：针对同一结果寻找不止一条路径，比较可能的替代与删除。状态：缺少系统级多路真实追踪。
- R06 执行续行：操作失败不能不当地变成全局停工；真正权限和风险不得被绕行。状态：受控覆盖有限；原生实际输出曾多次违反。
- R07 结果验收：仓库绿灯不等于用户和子域目标达成。状态：真实业务独立验收仍开放。
- R08 自主学习：从原始轨迹归纳适用条件、反例，检索到新任务并改进结果。状态：知识结构存在，迁移样本不足。
- R09 单一权威：不另造父总控、监控链、平行状态和高费用服务。状态：已有仓库约束。
- R10 主动使用能力：允许的插件、检索和工具应根据任务匹配，且观察真实动作结果。状态：可见插件不等于全部已授权。
- R11 每轮 Progress：准确引用当前任务与实际时间；不能口头称“完成”而漏报告。状态：已有契约、当前原生行为历史上有缺口。

这些不是“已知所有需求”的声明。缺失项通过用户业务实例、环境观察、异常场景和新专业来源持续发现。

## 5. 最小但完整的目标检验范例

案例：用户要求“所有回合都要全维度深入学习”。
- A（逐格门禁）：通过六维15名词、每格两个引用便允许完成；若真实理解错误，测试可能仍过。
- B（开放图探索）：先刻画漏判/自主性目标，挖掘多种架构和交互方案，以未知边界和产品结果证伪。更符合系统工程，但需要证明运行成本和广度。
- C（双重证据）：保留可审计来源足迹，同时检查重要关系、未知专业问题、用户实际成果和对照实验；目前的研究首选假说。
- NO_CHANGE：避免新风险，但保留当前 PR #163 的形式主义能力缺口。

**不立即晋级 C**。用陌生产品需求、单工具阻断、财经文章质量、视频跨平台身份漂移四类任务做对照，真实执行轨迹和验收结果决定。

## 6. 本专题蒸馏卡（候选）

`K-PRODUCT-01`：**不要把措施当目标**。触发：用户要求某个执行机制/框架/步骤；行动：先提取目标与约束，列竞争方案、证据和验收，再按当前权限选择。非适用：用户已明确且合法地指定唯一工具或不可改变的结果；不得为了“探索方案”擅自违背。验证：面对“六维每轮深研”的新场景是否识别并保留该明确约束，同时发现其不同于真正的业务目的。

`K-SYSTEM-02`：**受控代码成功 ≠ 原生宿主成功**。触发：跨宿主声明、PR 合并、SDK 门禁绿灯；验证：真实调用链、宿主证据、输出与任务结果。非适用：只声明该单元测试的单元行为。
