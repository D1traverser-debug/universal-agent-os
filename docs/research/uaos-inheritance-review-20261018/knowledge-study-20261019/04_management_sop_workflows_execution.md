# 04｜管理方法、SOP、业务工作流、调度恢复与行动闭环：专题知识库

归属：已有 UAOS 总控知识研究、任务及 Evolution；日期 2026-10-19；状态：SOURCE_STUDY/CANDIDATE。目的：把“遇到新问题应如何处理、什么事都要主动做”转为可执行且能适应新事件的总控工作模式，而不是另起一套流程或机械履历。

## 1. 基础术语：不能混用

- **管理方法**：如何持续保持目标、资源、责任和反馈对齐。如 OKR 关注目标衡量，PDCA 关注过程改进；彼此不等于工作流引擎。
- **方法论**：认识并解决问题的原则与证据要求，例如科学反证、系统工程、设计思维、根因分析；不是固定的工具调用清单。
- **SOP**：已经验证可重复的确定性操作步骤，适合稳定输入、产出和例外分支；新问题先学习，再经验证才能 SOP 化。
- **Workflow**：工作状态、行动、依赖、并行、事件、等待、失败、补偿、重试及恢复的可执行关系；可以调用 SOP，但不能由一份 SOP 表格代替。
- **Agent 控制/计划**：根据目标与新信息选择下一项动作；即使 SOP 不存在也应能合理研究和行动。
- **回顾/演化**：从实际执行结果更新方法、能力与约束；不是每次创建一项审批事务。

## 2. 学习的原始方法

### O01 — Toyota A3 and PDCA（ASQ）
https://asq.org/quality-resources/a3-report
- A3 用清晰的现状、目标、原因、对策、实施、验证和后续行动表达一个问题与改进；核心不是固定一张 A3 纸，而是去除无关信息。
- UAOS：针对反复“修小补丁但目标未改善”，保留问题事实、主要竞争根因、行动与效果闭环；不把每个回合变成一份新的 A3 报告。
- 风险：拿 A3 当绿灯模板可以全部填写却无真实行动；必须绑定实际收据。

### O02 — Scrum Guide（官方）
https://scrumguides.org/
- 经验主义强调透明、检视、适应，以及 Product Goal / Sprint Goal / Definition of Done 的不同含义。
- UAOS：把实际目标和交付标准分开；代码合并只是活动/中间产出，不是业务产品价值已达成。
- 非适用：不需要在每个 Agent 交互中设置 Scrum Master 或人为 Sprint 仪式。

### O03 — Google SRE postmortem culture
https://sre.google/workbook/postmortem-culture/
- 从真实故障轨迹整理可执行的防复发行动项，强调改进措施具有执行责任与反馈，而不仅是复盘总结。
- UAOS 迁移：对工具失败、错误判断、知识应用失败建立可证伪的修正；“提醒用户我知道了”不是事件恢复。
- 风险：每个普通问答都写长事故报告会吞噬任务成本。

### O04 — AWS operational excellence
https://docs.aws.amazon.com/wellarchitected/latest/operational-excellence-pillar/operational-excellence.html
- 组织围绕业务结果，产生可观测指标，安全地自动化，采用小而可逆的变更，并从运营事件持续学习。
- UAOS：自动化应附有授权、不确定结果对账和不可绕行的安全边界。减少重复手工提醒是明确的产品价值。
- 限制：不等于推荐新增 AWS 服务、云资源或订阅费。

### O05 — BPMN 2.0.2, OMG
https://www.omg.org/spec/BPMN/2.0.2/PDF
- 工作流事件、条件网关、并行、异常和补偿解释了正常路径与失败路径的状态差异。
- UAOS：把“单步骤失败”与“所有目标无法继续”严格区分；允许的其他分支继续执行。
- 不适用：现有状态机已经足以描述的业务流程无需迁移成 BPMN 引擎。

### O06 — Long-running agent harness
https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents
- 长任务跨会话会失去上下文，需明确状态、下一步和可恢复的执行产物；模型自称还记得不等于持久权威。
- UAOS：已有 TaskIndex 与 exact task state 承担断点，不新增第二套 active todo、进化监控或中间权威。
- 反例：已有 RUNNING 状态和 next_action，却没有真实宿主的自动调度，任务依然不动。

### O07 — Building effective agents
https://www.anthropic.com/engineering/building-effective-agents
- 固定流程适用于可明确分解的任务；真正 Agent 能动态选择工具/行动，复杂化只应在评价证据支持时增加。
- UAOS 不应把用户每个问题先匹配一个固定 SOP；应以动态目标/约束为核心，复用已验证的局部程序。

## 3. 工作流与 SOP 的融合：不是一张线性工序表

**外层持续任务循环：**
Observe (事实变化/状态/外部信息/自己的回答) →
Locate (目的、所有者、权限、已有知识) →
Investigate (需求/未知/因果/替代路线) →
Act (选择授权行动，可调 SOP、插件、工具、子域流程) →
Verify (工具收据+实际目标) →
Update (任务状态、可迁移方法、风险) →
Reassess (继续/合理等待/完成/回滚)。

这些标签是可互跳的动作类型，不强制每次按七个环节生成文档；同一事件可在研究中同时触发执行与纠错。

**内层 SOP 调用约束：**
目标适合稳定程序 + 当前前置条件匹配 + 已验证可用 + 动作允许 + 能观察结果 → 选择 SOP；遇到新异常 → 跳出 SOP，回到原因和备选方案探索。

**任务状态**（示意，不替代已有 kernel）：
`PLANNED → ELIGIBLE → RUNNING → VERIFIED → DONE`。
局部动作可为 `DENIED / UNKNOWN / RETRYABLE / WAITING_USER`，不直接覆写全任务 `RUNNING`；存在其他合法可行节点时继续。

## 4. 停工、恢复、并发与补偿的真实边界

情境 A：GitHub PR 写入被安全拒绝。不得换另一账户/工具执行同一被拒写入；可以执行独立且已授权的源码读取、业务分析和研究。此案例暴露“blocked operation != blocked whole objective”。

情境 B：发布接口响应 UNKNOWN，可能已经提交。不能立即重发副作用；用操作标识查询真实效果，再决定继续或补偿。这是幂等性与不确定提交处理，不是 SOP 模板能完全解决。

情境 C：需要用户确认文章目标价格/风险敏感权限，而独立调研可继续。只等待依赖选择的工作，不冻结全部任务。

情境 D：用户新指示与旧已冻结业务需求相冲突。应根据业务权威和变更流程记录差异、重新验证受影响产物，而非直接覆盖。

情境 E：任务已经结束且无新请求。可以明确完成；并非无限执行/无许可持续行动。

## 5. 管理方法的选择，不是全部安装

- **OKR / Product Goal**：总体结果和关键指标；不要把 CI 提交次数当成核心结果。
- **A3/PDCA**：问题模式反复或质量漂移时用于原因与改善对照。
- **Scrum/Kanban**：多项工作排期、WIP 和完成定义；不在对话内部增加冗余角色。
- **SRE**：异常事件响应、故障预防、可靠性目标、行动项。
- **BPMN / state machine**：跨系统、并发、等待与异常恢复的执行语义。
- **ADR / ATAM**：重大架构更改及备选路线决策与审计。
- **OODA**：高动态不确定环境中持续观察、定向、决定、行动；不能取代独立证据验证。

选择基于事务类型与已有 owner；同一案例可以组合方法，但不得新增互相争夺最终权威的流程。

## 6. 蒸馏方法卡

`K-OPERATE-01`：**作业的每个局部异常先判影响范围，重新评估仍可执行任务图；禁止将单动作拒绝扩大为全局任务停止。**
`K-SOP-02`：**经过不同任务实证的重复程序才 SOP 化；首次复杂问题应保留探索与竞争方案。**
`K-MANAGE-03`：**用最终业务目标与可观测结果检验管理机制，不用“创建了会议/表格/规则”作成功替代。**

## 7. 本专题不确定边界和下一步

来源角色涵盖质量管理、Scrum 官方、SRE、云运营官方、BPMN 标准和 Agent 工程；没有实际在生产部署的 UAOS 定时自主运行或跨会话完整追踪数据，因此目前只能证明方法研究和必要状态设计。下一步的独立任务实验需观察错误工具反馈与真实后续动作，而不是仅检验 SOP 字段是否齐全。
